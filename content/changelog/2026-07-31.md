## Per-project permissions (early access)

Neon's new permissions model is now in early access for all new organizations. Access works in two layers that combine additively, so a grant can only raise a user's access on a project, never lower it:

- **Organization roles** set a baseline across every project: **Admin** (full control), **Editor** (work in every project, but can't delete or transfer them), **Viewer** (read-only), and the new **Collaborator** role (no access until granted specific projects).
- **Per-project permissions** grant extra access on individual projects: **Viewer** (read-only), **Editor** (connect, query, and edit resources), and **Admin** (manage access, settings, and the project lifecycle).

Grant per-project permissions from a project's **Settings** &rarr; **Project permissions** page. When your organization moves to the new model, everyone keeps the access they have today: Admins stay Admins, Members become Editors, project creators become Admin on projects they created, and existing project-share access becomes Editor access. The new Collaborator role plus per-project permissions replaces project sharing, which is being deprecated.

To learn more, see [User permissions](/docs/manage/user-permissions).

- The `describe_table_schema` tool now supports schema-qualified table names, such as `crm.contacts`. Previously it resolved only tables in the `public` schema, so describing a table in another schema could return the wrong table or fail. A missing table now returns a clean "table not found" error.
