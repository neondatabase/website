## A new Console sidebar built around the Neon backend

The Console sidebar has a new shape. Neon is [more than a database now](/docs/get-started/backend-overview), and the old navigation still treated Postgres as the whole product. Every branch-level service now sits at the same level, so you pick a capability rather than hunting for it:

- **Postgres database** groups everything Postgres. Tables, SQL Editor, Backup & Restore, Computes, Data API, Roles, and Databases are now under one collapsible item instead of competing with each other for space in the sidebar.
- **Auth**, **Object storage**, **Functions**, and **AI Gateway** sit alongside it as siblings.

Above the divider, the sidebar separates what belongs to the whole project (Dashboard, Branches, Integrations, Settings) from what belongs to the branch you have selected (Overview, Credentials, Monitoring, Child branches). The branch picker sits between them, so it's clear which branch you're looking at when you open a service.

### A branch overview of every service

**Overview** is now a summary of the branch you have selected. It lists each backend service with its status, so you can see what the branch actually has enabled without opening each one:

| Service             | Details                                       |
| ------------------- | --------------------------------------------- |
| Postgres database   | 1 database, 1 compute                         |
| Managed Better Auth | Get user management via Better Auth           |
| Object storage      | Upload files and media to buckets             |
| Functions           | Deploy serverless functions next to your data |
| AI Gateway          | Access AI models from one credential          |

Anything not turned on yet shows without an **Enabled** badge, so the page doubles as a menu of what else you can add to the branch. Postgres monitoring sits below the table, and a side panel carries branch settings (region, plan, IP restrictions, VPC), Postgres settings (Data API, default compute range, history retention, Postgres version), and usage for the current billing period.

Nothing moved out of reach and no URLs changed. If you use Postgres and nothing else, your work is one click deeper and the rest of the sidebar tells you what else the branch can do.

Each service is available on any branch, and branching a project forks all of them together with your data:

- [Postgres](/docs/postgres/overview) and [Auth](/docs/auth/overview) are generally available in every Neon region.
- [Object Storage](/docs/storage/overview), [Functions](/docs/compute/functions/overview), and the [AI Gateway](/docs/ai-gateway/overview) are in beta.

<Admonition type="important" title="The beta services are in one region for now">
Object Storage, Functions, and the AI Gateway are available only in **AWS US East (Ohio) (`aws-us-east-2`)** while they're in beta, on new or existing projects in that region. More regions are coming soon.

If you don't see the new items in the sidebar, region is the most likely reason. Create a project in **US East (Ohio)**, or switch to one you already have there. Postgres and Auth work in any region. See the [backend beta guide](/docs/get-started/backend-beta) for the full access requirements.
</Admonition>

<Admonition type="note" title="Set up the Neon backend with your AI agent">
To build with the beta services, install the Neon agent skills so your assistant knows how to provision and wire them up:

```bash
npx neon@latest init
```

Then ask your assistant to get started with Neon. See the [backend beta guide](/docs/get-started/backend-beta) for access and setup, or [How a Neon backend fits together](/docs/get-started/backend-overview) for a tour of all five capabilities in one example app.
</Admonition>

## Project-level permissions are now available to all organizations

[Last week](/docs/changelog/2026-07-31#project-level-permissions) we brought project-level permissions to newly created organizations. Existing organizations have now been migrated, so every team on Neon has the four organization roles (**Admin**, **Editor**, **Viewer**, and **Collaborator**) and per-project permissions.

Your access carried over, and there was nothing to do:

- **Admins** stayed Admins.
- **Members** became **Editors**, with the same access under a new name.
- **Project creators** became **Admin** on the projects they created.
- People with **project-share access** became **Editor** on the projects shared with them.

Two things worth knowing now that you're on the new model:

- **Access is additive.** A per-project permission raises someone's access above their organization-role baseline, but it can't reduce it. There's no way to block an Editor from a single project. To limit someone to specific projects, give them the **Collaborator** role, which grants nothing by default, then grant permissions on just the projects they need.
- **Project sharing is being replaced** by the Collaborator role plus per-project permissions. Sharing still works, but grant new access with the new model instead. See the [project collaboration guide](/docs/guides/project-collaboration-guide).

Organizations created through the [Vercel-managed integration](/docs/guides/vercel-managed-integration) are the one exception. They stay on the legacy model for now, and will move over shortly.

New this week: [Get started with project permissions](/docs/manage/project-permissions-get-started) walks a small team from everyone-sees-everything to scoped access in about five minutes. It works through a concrete setup, giving a contractor access to one project without exposing production, and includes a copyable prompt if you'd rather have an AI assistant design and apply the structure for you.

For the reasoning behind the design, and why scoped access matters when you're handing projects to agents, read [Neon now has per-project permissions](/blog/neon-now-has-per-project-permissions) on our blog. See [User permissions](/docs/manage/user-permissions) for the full role reference.

## Manage API keys from the Neon CLI

The Neon CLI now has an `api-keys` command group, so you no longer have to visit the Console or hand-roll a `neon api` request to mint a key. All six API-key endpoints are covered:

<Admonition type="note" title="New to the Neon CLI?">
Install it with `npm install -g neon`, then authenticate with `neon auth`. See the [install guide](/docs/cli/install) and [CLI quickstart](/docs/cli/quickstart) to get going.
</Admonition>

```bash
neon api-keys list                                       # your account's keys
neon api-keys list --org-id org-example-12345678         # an organization's, with scope shown

neon api-keys create --name ci                                        # account key
neon api-keys create --name ci --org-id org-example-12345678          # organization key
neon api-keys create --name agent --project-id green-breeze-12345678  # one project only

neon api-keys revoke <id> --org-id org-example-12345678
```

Project-scoped keys are the reason this matters. A key created with `--project-id` can't create projects, can't mint more API keys, and can't see any other project. It isn't read-only, since inside that project it can do anything the API allows, but it bounds how far the credential reaches. That's what makes it safe to hand to an agent or a CI job instead of sharing your account:

```bash
neon link --project-id green-breeze-12345678   # once, as yourself
NEON_API_KEY=napi_… neon deploy                # then the agent, reaching only that project
```

The `api-keys` group deliberately ignores the linked directory in `.neon`. Every other project command fills in `--project-id` for you, which here would mean `neon api-keys create --name ci` quietly producing a key scoped to whatever project you have checked out rather than the account key you asked for. How far a credential reaches comes only from a flag you type.

See the [`neon api-keys` reference](/docs/cli/api-keys) for the full command reference, and [Manage API keys](/docs/manage/api-keys) for key types and permissions.

## Use more than one Neon account with CLI profiles

The Neon CLI could only hold one account at a time, so anyone working across a personal account and a work organization built their own workaround out of `--config-dir` and shell aliases. Profiles replace that. A profile is a name pointing at a credentials file:

```bash
neon auth --profile work        # create or re-authenticate
neon profiles list             # names, accounts, and where each one's credentials live
neon deploy --profile work     # or NEON_PROFILE=work
neon profiles remove work      # revoke the token, delete the file, drop the entry
```

Selection happens per invocation (`--profile`, then `NEON_PROFILE`, then `DEFAULT`), so there's no stored "active profile" to fall out of step with what you typed. If you only use one account, nothing changes: `DEFAULT` **is** `credentials.json` rather than a copy of it, and `profiles.json` is only created once a second profile exists.

A profile can also hold an API key instead of a browser session, which is what makes it useful for agents, shared machines, and CI:

```bash
neon profiles create work --api-key "$KEY"                          # store a key you already have
echo "$KEY" | neon profiles create work --api-key -                 # or pipe it, keeping it out of argv
neon profiles create ci --mint --project-id green-breeze-12345678   # sign in once, keep only a scoped key
neon profiles rotate-key ci                                         # mint a replacement at the same scope
neon --profile ci projects list                                     # no browser, ever
```

`--mint` is the flow worth knowing: one browser sign-in, a key minted with that session, only the key stored, and the session signed back out, so afterwards nothing about the profile can open a browser. The scope is recorded, so `rotate-key` mints its replacement at the same scope rather than quietly widening it.

The CLI also now stores its configuration in `$XDG_CONFIG_HOME/neon`, or `~/.config/neon` if that isn't set. An existing `neonctl` directory is still read in place. Nothing is moved, copied, or deleted, so there's no migration step and no second copy of a credential to go stale behind you.

<Admonition type="important" title="Behavior change when NEON_API_KEY is set">
An explicit flag now beats an environment variable, so `--profile` wins over `NEON_API_KEY`. If you run `neon --profile work` in an environment that exports `NEON_API_KEY`, the CLI resolves the profile and fails with `Unknown profile "work"` when no such profile exists. Previously the ambient key made that command appear to work while running as whoever the key belonged to. A pipeline that only injects `NEON_API_KEY` is unaffected.
</Admonition>

See the [`neon profiles` reference](/docs/cli/profiles) to get started.

## Serve WebSockets from a `fetch` handler on Neon Functions

[Neon Functions](/docs/compute/functions/overview) can now open a WebSocket from inside a `fetch` handler with `upgradeWebSocket`, added in `@neon/functions` 0.7.0. It returns `{ socket, response }`, mirroring `Deno.upgradeWebSocket`: `socket` is a standard `WebSocket`, and returning `response` from your handler completes the upgrade.

```ts
import { upgradeWebSocket } from '@neon/functions';

export default {
  fetch(request: Request) {
    const { socket, response } = upgradeWebSocket(request);

    socket.addEventListener('message', (event) => {
      socket.send(`echo: ${event.data}`);
    });

    return response;
  },
};
```

There's no separate export to add and no `ws` dependency to install. The existing `export function upgrade(req, socket, head)` shape keeps working unchanged, and takes precedence where both are present.

Local development caught up too. `neon dev` registered no `upgrade` listener, so Node handed WebSocket handshakes to the ordinary request handler and answered `200 OK` on a connection the client expected to be a `101`. Your `upgrade` export was never called, and the failure looked like success. The dev server now handles upgrades the way the deployed runtime does, so both patterns work locally for the first time. A function can also refuse a handshake by returning an ordinary `Response`, which is the normal case for an endpoint that rejects unauthenticated connections.

Update with `npm install neon@latest @neon/functions@latest`. See [WebSockets and SSE](/docs/compute/functions/websockets) for the full guide, including server-sent events and using Postgres `LISTEN/NOTIFY` to broadcast across isolates.

## New NAT gateway IPs and VPC endpoint services in Europe (Frankfurt)

We've expanded infrastructure capacity in the AWS Europe (Frankfurt) region (`eu-central-1`) with new NAT gateway IP addresses and new VPC endpoint service addresses for Private Networking.

<Admonition type="tip" title="Update your IP allowlists">
If you have IP allowlists on external systems that Neon connects to, **update those allowlists to include the new NAT gateway addresses**. Connections may be affected intermittently if traffic routes through non-allowlisted NAT gateways.
</Admonition>

If you use Private Networking in `eu-central-1`, you can now use the additional VPC endpoint service addresses for enhanced capacity and reliability. See the [Regions documentation](/docs/introduction/regions#aws-nat-gateway-ip-addresses) for the complete list of NAT gateway IPs and the [Private Networking guide](/docs/guides/neon-private-networking) for VPC endpoint service addresses by region.
