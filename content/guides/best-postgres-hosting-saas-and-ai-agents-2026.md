A growing share of Postgres databases aren't long-running production apps. They're previews, experiments, and apps an AI agent built in a few minutes, and many of them become idle soon. AI agents now create [over 80% of the databases on Neon](https://www.databricks.com/company/newsroom/press-releases/databricks-agrees-acquire-neon-help-developers-deliver-ai-systems).

On a host that bills each database as an always-on instance, every one of those copies costs as much as production, whether anyone uses it or not. And a copy of the database alone isn't enough, because the app also needs its files, its users, and its backend code.

This guide compares five Postgres hosts on what those databases cost, from idle apps to short-lived copies of production, and on how each host copies the rest of the backend along with the data, so developers and agents can iterate faster.

## What do you need from Postgres hosting?

At a minimum, Postgres hosting for a modern app should give you:

- **Managed Postgres** with backups, point-in-time restore, and connection pooling.
- **Predictable pricing** you can estimate before your app grows.
- **A usable free tier** to build and test a real app before you pay.

For teams that open many pull requests and agents that run many experiments, the options that stand out add:

- **Branching with data:** A pull request or agent run gets a copy of production data in under a second, without a dump and restore.
- **Object storage that branches too:** Files uploaded or generated by your app are copied into each branch along with the rows that reference them.
- **Functions that branch too:** Backend code deploys to each branch and runs next to its data, so a preview or agent run tests the code and the database together.
- **A built-in AI gateway:** One credential for models from several providers, so each branch can test a new model or prompt without a new API key.
- **Usage-based billing:** Idle preview and experiment environments cost little or nothing.

## What's the best Postgres hosting for SaaS and AI agents?

### 1. Neon

[Neon](/docs/introduction) is a cloud with backend primitives built around Lakebase Postgres. What sets it apart from a typical Postgres host is that a [branch](/docs/introduction/branching) in Neon copies all of it in under a second: the database, the [Managed Better Auth](/docs/auth/overview) users, the files in [Object Storage](/docs/storage/overview), the [Functions](/docs/compute/functions/overview) deployment, and the [AI Gateway](/docs/ai-gateway/overview) endpoint.

That turns a copy-on-write branch into a sandbox an agent can manage on its own. Through the [Neon MCP server](/docs/ai/neon-mcp-server), an agent can create a branch, run its migrations there, and delete the branch when it's done. A few patterns that work especially well with such a backend:

- **Parallel experiments:** Each branch gets its own compute, so an agent can test three fixes on three branches in parallel and keep the one that works.
- **Model testing:** Each branch has its own AI Gateway endpoint, so an agent can compare a new model or prompt against real data while production keeps calling the old one.
- **One-step reset:** If an attempt goes wrong, [reset the branch from its parent](/docs/guides/reset-from-parent) to get the parent's latest schema and data back without creating a new branch.

Let's walk through setting up an agent backend on Neon and giving an agent run its own copy of it.

#### Declare the backend as code

The AI Gateway, a bucket, and a function are declared in [`neon.ts`](/docs/reference/neon-ts), next to the rest of your Neon setup:

```typescript filename="neon.ts"
import { defineConfig } from '@neon/config/v1';

export default defineConfig({
  aiGateway: true,
  buckets: { reports: {} },
  functions: {
    agent: { name: 'Report agent', source: './functions/agent.ts' },
  },
});
```

Running `neon link` and then `neon deploy` enables the AI Gateway, creates the bucket, deploys the function on the linked branch, and writes `DATABASE_URL` and the `AWS_*` S3 credentials into your local `.env`.

#### Build an agent with Postgres, Object Storage, and AI Gateway

The function below reads rows from Postgres, asks a model through the AI Gateway to summarize them, saves the summary to Object Storage, and records the file's key in Postgres. The `@neon/ai-sdk-provider` reads the gateway credentials that Neon injects into the function, so you don't need a provider API key:

```typescript filename="functions/agent.ts" shouldWrap
import { neon } from '@neon/ai-sdk-provider';
import { attachDatabasePool } from '@neon/functions';
import { generateText } from 'ai';
import { Files } from 'files-sdk';
import { neon as neonStorage } from 'files-sdk/neon';
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 5 });
attachDatabasePool(pool);

const files = new Files({ adapter: neonStorage({ bucket: 'reports' }) });

export default {
  async fetch(request: Request) {
    const { accountId } = await request.json();
    const { rows } = await pool.query('SELECT * FROM invoices WHERE account_id = $1', [accountId]);

    const { text } = await generateText({
      model: neon('gpt-5-mini'),
      prompt: `Summarize these invoices: ${JSON.stringify(rows)}`,
    });

    const key = `reports/${accountId}.md`;
    await files.upload(key, Buffer.from(text), { contentType: 'text/markdown' });
    await pool.query('INSERT INTO reports (account_id, object_key) VALUES ($1, $2)', [accountId, key]);

    return Response.json({ key });
  },
};
```

A Neon Function has 15 minutes to send its first byte, then keeps a response stream open as long as data flows, with 2,048 MiB of memory ([runtime limits](/docs/compute/functions/reference/runtime-limits)). That covers agents that chain many model and tool calls before they respond.

#### Give every agent run its own copy

Before a risky run, the agent creates a branch, deploys the code it wants to test to that branch, and calls the branch's function:

```bash
neon branches create --name agent-run-42
neon deploy --branch agent-run-42
```

The run reads and writes its own copy of the rows and files, and calls models through its own gateway endpoint, while production stays untouched. When the run ends, the agent uses the following to remove the database, files, and function deployment together:

```bash
neon branches delete agent-run-42
```

**Strengths:**

- Branches copy the database, auth, files, functions, and AI Gateway, and bill only for the data they change
- Idle computes scale to zero, so unused previews and agent branches cost only their storage
- Functions that stream past 15 minutes, long enough for agents that chain many model calls
- One credential for OpenAI, Google, and other models, with no provider API keys to manage
- Instant restore on the same connection string, with a backup branch to undo it

**Watch out for:**

- High availability covers Availability Zones in one region, with no cross-region replication
- Functions and Object Storage are available in four AWS regions today

<Admonition type="tip" title="Best for">
SaaS teams and agent builders who want every pull request, preview, and agent run to get its own copy of the backend, with production data and files, in under a second.
</Admonition>

### 2. Amazon RDS for PostgreSQL

**Amazon RDS for PostgreSQL** is the oldest managed Postgres service in this list. It has the widest range of instance options here: classes from 1 GiB to 4,096 GiB of RAM, Multi-AZ deployments, read replicas, and up to 35 days of point-in-time recovery.

RDS has no branching, so to give a pull request or an agent run its own copy, you restore a snapshot or a point in time to a new DB instance with its own endpoint. The new instance becomes available and then loads its data blocks from Amazon S3 in the background, so queries run slower until loading finishes.

An instance can't scale to zero: you can stop it for up to 7 days to stop paying for instance hours, but you still pay for its storage, and RDS starts it again automatically after 7 days.

**Rest of the backend:**

- **Auth:** Amazon Cognito user pools (10K MAU free, then $0.0055/MAU)
- **Files:** Amazon S3 ($0.023/GB-month)
- **Functions:** AWS Lambda, connected to the database through your VPC and often RDS Proxy ($0.20 per 1M requests, plus duration)
- **Model access:** Amazon Bedrock (per token, by model)

**Strengths:**

- Free backup storage up to your provisioned size, so most backups cost nothing extra
- Runs in your own AWS account and VPC, inside your existing network and security setup
- Per-second billing with a 10-minute minimum, so a short-lived restored copy bills only for the time it runs

**Watch out for:**

- No branching (every copy is a new instance restored from a snapshot or a point in time)
- Instances bill every hour they run and can't scale to zero
- Auth, files, functions, and model access are separate AWS services that don't branch with the database

<Admonition type="tip" title="Best for">
Teams already on AWS that run a few long-running databases on fixed instances, and whose previews and agents can work with seed data or wait for a restore.
</Admonition>

### 3. DigitalOcean Managed PostgreSQL

**DigitalOcean Managed PostgreSQL** is the managed Postgres service on DigitalOcean. It's built for simple, predictable setups: fixed plans, daily backups, 7 days of point-in-time recovery, connection pooling, and standby and read-only nodes. Starting October 15, 2026 for new accounts, and November 30, 2026 for all accounts, new Standard Edition clusters can't use plans with more than 4 GiB of RAM or add standby or read-only nodes.

DigitalOcean has no branching, so to give a pull request or an agent run its own copy, you fork the cluster from its latest state or any point in the last 7 days. A fork is a new cluster that copies the source's data and settings while it's provisioned, so it takes longer than creating an empty cluster, and it bills like any other cluster for as long as it exists. Each account starts with a limit of 10 clusters.

A cluster can't scale to zero or pause. To stop paying for it, you destroy it, which also deletes its automated backups.

**Rest of the backend:**

- **Auth:** no managed service, so an auth library in your app or a third-party provider (priced by the provider you pick)
- **Files:** Spaces, which works with standard S3 SDKs ($5/month for 250 GiB)
- **Functions:** DigitalOcean Functions (up to 15 minutes and 1 GB of memory, $0.0000185/GiB-second after 90K free), or App Platform for longer-running work
- **Model access:** DigitalOcean Serverless Inference (provider rates, prepaid)

**Strengths:**

- Flat monthly plans with daily backups and 7-day point-in-time recovery included
- Database traffic isn't billed as bandwidth, so heavy reads don't add transfer charges
- One key for OpenAI, Anthropic, and other models through DigitalOcean Serverless Inference

**Watch out for:**

- No branching, so every copy is a forked cluster that bills for as long as it exists
- Clusters can't scale to zero or pause
- No managed auth, and files, functions, and model access aren't copied when you fork the database

<Admonition type="tip" title="Best for">
Teams already on DigitalOcean that run a few always-on databases on flat monthly plans, and whose previews and agents can wait for a fork.
</Admonition>

### 4. Cloud SQL for PostgreSQL

**Cloud SQL for PostgreSQL** is the managed Postgres service on Google Cloud. Each database runs on a fixed instance in one of two editions: Enterprise, or Enterprise Plus with up to 128 vCPUs, 864 GiB of RAM, and 35 days of point-in-time recovery. Both offer high availability, and Enterprise also has shared-core machine types for small databases.

Cloud SQL has no branching, but it can clone an instance. A fast clone in the same zone creates a new instance from an Instant Snapshot in seconds to minutes, whatever the data size. A clone from a point in time uses a standard clone instead, which copies a full backup and takes time proportional to the database size. Either way, the clone is a separate instance with its own IP address and the source's machine type, so it bills as a full instance for every second it runs. A project can hold up to 1K instances.

Instances don't scale to zero: a stopped instance stops billing for the instance but keeps billing for storage and IP addresses, and it stays stopped until you start it.

**Rest of the backend:**

- **Auth:** Identity Platform or Firebase Authentication (50K MAU free, then $0.0055/MAU)
- **Files:** Cloud Storage ($0.020/GB-month)
- **Functions:** Cloud Run functions, with a built-in connection to Cloud SQL ($0.40 per 1M requests, plus CPU and memory time)
- **Model access:** Gemini Enterprise Agent Platform (per token, by model)

**Strengths:**

- Fast clones in seconds to minutes, whatever the data size
- Up to 128 vCPUs, 864 GiB of RAM, and 35 days of point-in-time recovery on Enterprise Plus
- Up to 1K instances per project, enough for a database per customer

**Watch out for:**

- Each clone is a full instance with the source's machine type, billed while it runs, and a point-in-time clone takes time proportional to the database size
- Instances can't scale to zero, and the cheapest shared-core instances aren't covered by the SLA
- Auth, files, functions, and model access are separate Google Cloud services that aren't copied with the database

<Admonition type="tip" title="Best for">
Teams already on Google Cloud that run a few long-running databases, and that can give each preview or agent run a full clone of the production instance.
</Admonition>

### 5. Supabase

**Supabase** bundles Postgres with Storage, Auth, and Edge Functions into a project. Every project runs on a fixed instance size, starting at Micro (1 GB of RAM), that's billed every hour of the month.

Supabase has branching on paid plans, billed per branch per hour. A new branch starts from your migrations and seed data. The **Include data** option copies production data into the branch, but it requires the paid point-in-time recovery add-on, and it doesn't copy storage objects, so every branch starts with empty buckets.

Edge Functions stop after 400 seconds on paid plans (150 seconds on Free), with 256 MB of memory and 2 seconds of CPU time per request. Supabase has no AI gateway, so each environment needs its own provider API keys.

**Rest of the backend:**

- **Auth:** Supabase Auth, with 50K monthly active users on Free and 100K on Pro (then $0.00325/MAU)
- **Files:** Storage, which supports the S3 protocol, with row-level security policies for access (100 GB on Pro, then $0.0213/GB)
- **Functions:** Edge Functions in the same project (2M invocations on Pro, then $2 per 1M)
- **Model access:** each provider's API key, stored as an Edge Function secret (the provider's own pricing)

**Strengths:**

- Storage, Auth, and Functions managed together in one project
- 100 GB of file storage, 250 GB of egress, and 2M Edge Function invocations a month included on Pro
- Predictable monthly pricing for a single always-on project

**Watch out for:**

- Branches with production data need the paid point-in-time recovery add-on, and storage objects aren't copied
- Edge Functions stop after 400 seconds, which cuts off longer agent runs
- Every project and branch runs on a fixed instance billed by the hour, whether or not it's used

<Admonition type="tip" title="Best for">
Teams already on Supabase whose previews need only seed data, and whose functions finish within 400 seconds.
</Admonition>

## Which Postgres host should you choose?

- **Is your team already on Supabase, with functions that finish within 400 seconds?** Choose **Supabase**.
- **Do you run a few always-on databases and want flat monthly plans with backups and database traffic included?** Choose **DigitalOcean Managed PostgreSQL**.
- **Do your customers, such as law firms, clinics, or banks, expect their data to stay apart from everyone else's?** Choose **Neon**, since a separate project per customer has no per-project fee and scales to zero ([see the cost](#a-document-assistant-for-law-firms)).
- **Are you already on AWS and running a few long-running databases on fixed instances?** Choose **Amazon RDS for PostgreSQL**.
- **Are you already on Google Cloud and want full clones of a production instance?** Choose **Cloud SQL for PostgreSQL**.
- **Do your agents need to test new code and models against real data?** Choose **Neon**, since each branch gets its own function deployment and AI Gateway endpoint, with one credential for OpenAI, Google, and other models.
- **Are you worried an agent will run a destructive command on production?** Choose **Neon**, since instant restore puts the database back in seconds on the same connection string ([see how](/docs/postgres/backup-restore/branch-restore)).
- **Are you building an app builder where most generated apps sit unused after a few days?** Choose **Neon**, since an unused app costs only its storage ([see the cost](#an-ai-app-builder-like-replit)).
- **Do your developers or coding agents need real data to test each change against?** Choose **Neon**, since a branch copies the database and files in under a second ([see the cost](#a-team-that-reviews-every-pull-request-against-production-data)).

### Recommendations by team type

#### For solo developers and hackathon teams

- **Neon** for 100 free projects, each with 100 CU-hours, 1 GB of Postgres storage (up to 20 GB across all projects), 5 GB of Object Storage, and a Functions allowance, and nothing to pay while a project is idle
- **Cloud SQL for PostgreSQL** for a free 30-day trial instance (8 vCPUs, 64 GB of RAM, and 100 GB of storage) on top of $300 of credits for 90 days, if your project only needs to run for the length of the event

#### For early-stage AI startups

- **Neon** for no base fee, one AI Gateway credential for OpenAI, Google, and other models, functions that deploy to every branch, and a branch with production data on every pull request
- **DigitalOcean Managed PostgreSQL** for flat plans from $15.15 a month with backups included, and one key for OpenAI and Anthropic models through DigitalOcean Serverless Inference, if your previews can wait for a fork

#### For AI app builders and agent platforms

- **Neon** for a database per generated app that costs only its storage while it's unused, 1K projects on Scale, and the [Agent Plan](/docs/introduction/agent-plan) with unlimited projects and Launch-rate compute
- **Supabase** if each generated app needs storage, auth, and functions in one project, and an always-on Micro instance per app fits your budget

#### For teams that use coding agents on their own codebase

- **Neon** for a branch per agent task with production data and files, the [Neon MCP server](/docs/ai/neon-mcp-server) so agents can create and delete branches themselves, and instant restore if an agent breaks production
- **DigitalOcean Managed PostgreSQL** for a fork per agent task, if each task can wait for the fork and the file copy before it starts

#### For AI companies in legal, healthcare, and finance

- **Neon** for a separate project per customer, so you can restore or delete one customer's data without touching anyone else's. The Scale plan adds [HIPAA](/docs/security/hipaa), on top of Neon's [SOC 2, ISO 27001, ISO 27701, and GDPR compliance](/docs/security/compliance)
- **Amazon RDS for PostgreSQL** for Multi-AZ deployments and up to 35 days of point-in-time recovery, in your own AWS account and VPC

#### For agencies that build apps for clients

- **Neon** for a project per client at no per-project fee, and [project transfer](/docs/manage/orgs-project-transfer) to give a finished project to the client's own organization
- **Supabase** if your clients want storage and auth in the same project and one always-on instance each fits their budget

#### For B2B SaaS teams with growing traffic

- **Supabase** if the Pro plan's bundled storage, egress, and function allowances fit your usage
- **Amazon RDS for PostgreSQL** if you're already on AWS and your traffic is steady enough for Reserved Instances or Database Savings Plans
