The [Neon Data API](/docs/data-api/overview) exposes your database as a REST endpoint authorized by JWTs and [Row-Level Security (RLS)](/docs/guides/row-level-security). A [TanStack Router](https://tanstack.com/router) single-page app can query it straight from the browser, with [Managed Better Auth](/docs/auth/overview) issuing the JWTs. There is no backend to deploy.

<Admonition type="important" title="Secure your data before exposing it">
The Data API has no permission layer of its own. Every request is authorized by your Postgres `GRANT` statements and RLS policies, so a table without a policy is exposed to any signed-in user. Follow [Access control & security](/docs/data-api/access-control) and run the [Data API advisors](/docs/data-api/database-advisor) before exposing data.
</Admonition>

Use TanStack Start server functions instead when you need logic that the database can't enforce, secrets, or calls to other services. See [Postgres with Drizzle for TanStack Start](/docs/tanstack/postgres-drizzle).

## Enable the Data API and Managed Better Auth

```bash filename="Terminal"
neon config add data-api
neon deploy
```

Or, in the Neon Console, select **Postgres database** > **Data API**, check **Use Neon Auth** and **Grant public schema access**, and click **Enable Data API**. Add your app's origins with `neon neon-auth domain add <origin>`.

## Create a table with RLS

```sql
CREATE TABLE todos (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id text DEFAULT (auth.user_id()) NOT NULL,
  title text NOT NULL,
  completed boolean NOT NULL DEFAULT false
);

ALTER TABLE todos ENABLE ROW LEVEL SECURITY;

CREATE POLICY manage_own_todos ON todos
FOR ALL TO authenticated
USING (auth.user_id() = user_id)
WITH CHECK (auth.user_id() = user_id);
```

`auth.user_id()` returns the JWT `sub` claim, so each user reads and writes only their own rows. After schema changes, refresh the Data API schema cache. See [Getting started with Neon Data API](/docs/data-api/get-started#refresh-schema-cache).

## Create the client

```bash filename="Terminal"
npm install @neon/neon-js
```

```ts filename="src/neon.ts"
import { createClient } from '@neon/neon-js';

// The HTTPS Neon database URL, not the Postgres connection string.
// Example: https://ep-example.c-2.us-east-1.aws.neon.tech/neondb
export const neon = createClient(import.meta.env.VITE_NEON_DATABASE_URL);
```

`createClient()` derives the Managed Better Auth and Data API URLs from the database URL and attaches the signed-in user's JWT to every query.

## Sign in and guard routes

```tsx filename="src/routes/_authenticated.tsx"
import { createFileRoute, redirect } from '@tanstack/react-router';

import { neon } from '../neon';

export const Route = createFileRoute('/_authenticated')({
  beforeLoad: async ({ location }) => {
    const { data: session } = await neon.auth.getSession();
    if (!session) {
      throw redirect({ to: '/sign-in', search: { redirectTo: location.href } });
    }
    return { user: session.user };
  },
});
```

```ts
await neon.auth.signUp.email({ email, password, name });
await neon.auth.signIn.email({ email, password });
await neon.auth.signOut();
```

## Query in loaders

```tsx filename="src/routes/_authenticated/todos.tsx"
import { createFileRoute } from '@tanstack/react-router';

import { neon } from '../../neon';

export const Route = createFileRoute('/_authenticated/todos')({
  loader: async () => {
    const { data, error } = await neon.from('todos').select('id, title, completed').order('id');
    if (error) throw error;
    return data;
  },
  component: TodosPage,
});

function TodosPage() {
  const todos = Route.useLoaderData();
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>{todo.title}</li>
      ))}
    </ul>
  );
}
```

Writes use the same client. RLS fills in and checks `user_id`:

```ts
const { error } = await neon.from('todos').insert({ title: 'Ship it' });
if (error) throw error;
await router.invalidate();
```

To generate TypeScript types for your tables, see [Generate types](/docs/data-api/generate-types).

## Common pitfalls

| Pitfall                                   | Fix                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| A table without RLS                       | Enable RLS on every table in an exposed schema and add policies before shipping.           |
| Passing the Postgres connection string    | Pass the HTTPS Neon database URL. The connection string holds a password.                  |
| Treating the route guard as authorization | The guard only controls navigation. RLS is what stops a signed-in user reading other rows. |
| Stale results after a schema change       | Refresh the Data API schema cache.                                                         |
