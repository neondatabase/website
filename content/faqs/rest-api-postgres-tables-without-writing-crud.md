Use the Neon [Data API](/docs/data-api/overview). It turns the tables in your Lakebase Postgres database into REST endpoints that speak the PostgREST protocol, so `GET /rest/v1/posts?is_published=eq.true` runs a query and returns JSON. There's no server to write or deploy: you enable it on a branch, write Row-Level Security policies, and call it from a browser, a mobile app, an edge function, or `curl` ([get started](/docs/data-api/get-started)).

## Why hand-written CRUD gets expensive

A typical app ends up with dozens of near-identical handlers: parse the request, check who the user is, build a query, serialize the result. Each one is a place to forget an ownership check, and each schema change means editing handlers too. Axess Intelligence put it this way after replacing that layer: "We didn't want to spend unnecessary time writing CRUD logic or maintaining a backend" ([case study](/blog/how-axess-intelligence-simplified-their-backend-with-neons-data-api)).

## How the Data API replaces the handlers

The Data API has no permission layer of its own. Each request carries a JWT, the API switches to the Postgres role named in the token's `role` claim (usually `authenticated`), and your `GRANT` statements and RLS policies decide what that role can see and change ([access control](/docs/data-api/access-control)). The ownership check you'd write in every handler becomes one policy:

```sql
CREATE TABLE posts (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id text DEFAULT (auth.user_id()) NOT NULL,
  content text NOT NULL,
  is_published boolean DEFAULT false,
  created_at timestamptz DEFAULT now() NOT NULL
);

ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

CREATE POLICY manage_own_posts ON posts
FOR ALL TO authenticated
USING (auth.user_id() = user_id)
WITH CHECK (auth.user_id() = user_id);
```

`auth.user_id()` returns the token's `sub` claim, so inserts are stamped with the caller's ID and reads only return their rows ([get started](/docs/data-api/get-started#create-a-table-with-rls)). From the client, [`@neon/neon-js`](/docs/reference/javascript-sdk) gives you a query builder with `select`, `insert`, `update`, `delete`, filters, and `rpc` for Postgres functions:

```ts
import { createClient } from '@neon/neon-js';

const client = createClient(import.meta.env.VITE_NEON_DATABASE_URL);

const { data, error } = await client
  .from('posts')
  .select('*')
  .eq('is_published', true)
  .order('created_at', { ascending: false });
```

With [Managed Better Auth](/docs/auth/overview) as the provider, the client attaches the signed-in user's token automatically. Other providers that issue JWTs work too through a JWKS URL ([custom providers](/docs/data-api/custom-authentication-providers)). For type safety, `npx @neondatabase/neon-js gen-types` writes TypeScript types from your schema ([generate types](/docs/data-api/generate-types)).

## Turning it on

Enable it in the Console under **Postgres database** > **Data API**, with `neon data-api create`, through the Neon API, or with the MCP server's `provision_neon_data_api` tool ([get started](/docs/data-api/get-started#enable-the-data-api)). To keep it in code, declare `dataApi: true` alongside `auth: true` in [`neon.ts`](/docs/reference/neon-ts#dataapi) and run `neon deploy`; `neon env pull` then writes `NEON_DATA_API_URL` to your `.env`. The Console option to grant the `authenticated` role read and write access on the `public` schema applies the default `GRANT`s for you.

The API is enabled per branch for a single database, and each branch gets its own URL. A preview branch can run the same frontend against its own copy of the data and the same policies ([get started](/docs/data-api/get-started#before-you-begin)).

## Limits to know

- Tables with RLS disabled are readable by every authenticated user. Run the [Data API advisors](/docs/data-api/database-advisor) to catch tables exposed without RLS.
- After schema changes, refresh the schema cache from the Console, the API, or `neon data-api refresh-schema` ([manage](/docs/data-api/manage#manage-via-the-neon-cli)).
- Logic that doesn't fit in SQL, like calling a third-party API, belongs in a [Function](/docs/compute/functions/overview) next to the database.
- The Data API doesn't support projects with IP Allow or Private Networking enabled.

## How other options compare

- **Self-hosted PostgREST**: a standalone web server that turns a Postgres database into a REST API, with endpoints and permissions taken from the database ([PostgREST docs](https://docs.postgrest.org/en/stable/)). You run and scale the server yourself. Neon's Data API speaks the same protocol, so existing PostgREST clients only need a new endpoint and auth configuration ([announcement](/blog/a-postgrest-compatible-data-api-now-on-neon)).
- **Supabase**: auto-generates a REST API from your schema with PostgREST, served at `https://<project_ref>.supabase.co/rest/v1/` and working with Row Level Security ([Supabase Data REST API](https://supabase.com/docs/guides/api)).
