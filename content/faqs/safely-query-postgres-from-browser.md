Use Neon. You can't put a database connection string in a browser bundle: anyone who opens dev tools gets full access as that role. The [Neon Data API](/docs/data-api/overview) gives your Lakebase Postgres database an HTTPS REST endpoint that frontends call with the user's JWT instead. Every request runs as a Postgres role named in the token, so your database, not a hand-written API layer, decides what each user can read and write.

## The Data API has no permission layer of its own

That's the part to get right. Access is decided entirely by Postgres, in two layers ([access control](/docs/data-api/access-control)):

1. **Table privileges (`GRANT`).** Which tables the role can read or write. Requests from signed-in users run as `authenticated`. Requests with no `role` claim run as `anonymous`, which has no permissions until you grant some.
2. **Row-Level Security (RLS).** Which rows the role sees. `auth.user_id()` returns the `sub` claim from the request's JWT, so a policy can limit each user to their own rows.

How RLS is set on a table changes what a signed-in user sees:

| RLS state            | What an authenticated user gets |
| -------------------- | ------------------------------- |
| Disabled             | Every row in the table          |
| Enabled, no policies | Nothing                         |
| Enabled + policies   | Only rows the policies allow    |

A table with `SELECT` granted and RLS disabled is readable in full by any signed-in user. That's the most common mistake.

## A safe default for a user-owned table

```sql
CREATE TABLE notes (
  id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id text NOT NULL DEFAULT (auth.user_id()),
  body    text NOT NULL
);

ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY "own notes" ON notes
  FOR ALL TO authenticated
  USING ((select auth.user_id()) = user_id)
  WITH CHECK ((select auth.user_id()) = user_id);
```

The default fills `user_id` from the token on insert, and the policy covers reads and writes. Wrapping `auth.user_id()` in `select` lets Postgres evaluate it once per query instead of once per row, a pattern the advisors check for. For public data such as a product list, grant `SELECT` to `anonymous` on that table only. See [secure your app with RLS](/docs/guides/rls-tutorial) for a full walkthrough.

## Let the advisors check your schema

Because the Data API exposes your schema directly over HTTP, misconfigurations that an app server would hide become reachable. The [Data API Advisors](/docs/data-api/database-advisor) run checks from the Console or the API and flag, among others, exposed tables with RLS disabled, tables with policies but RLS off, sensitive columns exposed, security definer views, policies that always return true, and RLS enabled with no policy. Run them before you ship and after schema changes.

## Endpoint settings that help

In the Data API settings ([manage the Data API](/docs/data-api/manage)):

- **Exposed schemas.** Only `public` by default. Keep internal tables in a schema you don't expose.
- **Maximum rows per request.** A hard cap on rows per response, so a client can't pull a whole table in one call.
- **CORS allowed origins.** Empty allows any origin. List your production domains so other websites can't call the API from a browser. CORS only governs browsers, so it complements RLS rather than replacing it.

## Where the tokens come from

[Managed Better Auth](/docs/auth/overview) issues JWTs with the `authenticated` role claim automatically, and the `@neon/neon-js` client sends them on every query. If you already use Clerk, Auth0, Firebase, or another provider, configure it as a [custom authentication provider](/docs/data-api/custom-authentication-providers); its tokens must carry the `role` claim. See [using third-party JWTs with RLS](/faqs/use-clerk-auth0-firebase-jwt-postgres-rls).

## Test policies on a branch

Policies are part of your schema, so they branch with your data. The Data API is configured per branch, so create a branch from production, enable the Data API there, and try requests as different users before changing production ([get started](/docs/data-api/get-started)).
